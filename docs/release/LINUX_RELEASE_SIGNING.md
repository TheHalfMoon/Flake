# Linux production release-signing (GPG)

Plan section 25's "Linux/checksum manifests ... using owner-controlled credentials without
exposing them" clause does not require a commercial certificate authority — a GPG key
controlled by the project is the standard, legitimate mechanism Linux distributions and
package managers already expect (`gpg --detach-sign` / `gpg --verify`). This document is the
complete architecture: identity, one-time key generation, CI secret injection, verification,
and rotation/revocation.

## 1. Identity

```text
Flake Release Signing <285091250+TheHalfMoon@users.noreply.github.com>
```

Fixed by `docs/canonical/FOUNDER_RELEASE_SIGNING_IDENTITY_DECISION_2026-09-18.md`. This is a
production identity, distinct in name and email from every disposable per-run test identity
`scripts/release/sign_linux.sh`'s `TEST_SIGNING_MODE=1` path generates (`Flake TEST Signing Key
- NOT PRODUCTION - disposable <ci-disposable-test@invalid.example>`, expires in 1 day, deleted
at the end of every run) — the two can never be confused by name, email, or lifetime.

**Fingerprint:** recorded here once the key exists (§2). Until then this field reads
`NOT_YET_GENERATED`.

```text
FLAKE_RELEASE_SIGNING_FINGERPRINT=NOT_YET_GENERATED
```

## 2. One-time key generation (Founder-run, local, NOT in an agent session)

Generating a real, long-lived production private key inside an agent tool-call transcript
would place that key material in session logs — exactly the exposure this project's signing
policy forbids (`docs/release/CODE_SIGNING_POLICY.md`). The key must instead be generated by
the Founder, once, on a machine and shell session that is not being transcribed by an agent.

Run this exactly once, on a trusted, offline-capable machine:

```bash
# 1. Generate the key (modern, supported algorithm: Ed25519 signing + Cv25519 encryption
#    subkey; a real production key SHOULD carry a strong passphrase, unlike the disposable
#    test keys the CI mechanics test uses).
gpg --batch --gen-key <<'EOF'
%ask-passphrase
Key-Type: EDDSA
Key-Curve: ed25519
Subkey-Type: ECDH
Subkey-Curve: cv25519
Name-Real: Flake Release Signing
Name-Email: 285091250+TheHalfMoon@users.noreply.github.com
Expire-Date: 2y
%commit
EOF

# 2. Record the fingerprint (paste it into this file's §1 and into
#    docs/release/RELEASE_VERIFICATION.md).
gpg --list-secret-keys --with-colons "285091250+TheHalfMoon@users.noreply.github.com" \
  | awk -F: '/^fpr:/ {print $10; exit}'

# 3. Create a revocation certificate NOW, before any production use, and store it offline
#    (e.g. a password manager attachment or offline encrypted volume) -- never in this
#    repository.
gpg --gen-revoke --output flake-release-signing-revocation.asc \
  "285091250+TheHalfMoon@users.noreply.github.com"

# 4. Export the public key (safe to publish) and the armored private key (secret material --
#    goes only into the GitHub Actions encrypted secret in step 5, never a file the repo
#    tracks).
gpg --armor --export "285091250+TheHalfMoon@users.noreply.github.com" \
  > flake-release-signing-public.asc
gpg --armor --export-secret-keys "285091250+TheHalfMoon@users.noreply.github.com" \
  > /tmp/flake-release-signing-private.asc   # never commit; delete after step 5

# 5. Store as GitHub Actions repository secrets (Settings -> Secrets and variables ->
#    Actions -> New repository secret), then delete the local temp file:
#      GPG_PRIVATE_KEY       = contents of /tmp/flake-release-signing-private.asc
#      GPG_KEY_PASSPHRASE    = the passphrase chosen in step 1
#      GPG_KEY_FINGERPRINT   = the fingerprint from step 2 (pins CI to this exact key --
#                              scripts/release/sign_linux.sh refuses to sign if the key it
#                              actually imports does not match)
shred -u /tmp/flake-release-signing-private.asc   # or securely delete by your OS's means

# 6. Commit flake-release-signing-public.asc into the repository (e.g.
#    docs/release/flake-release-signing-public.asc) and record the fingerprint in this file
#    and in docs/release/RELEASE_VERIFICATION.md. The revocation certificate from step 3 is
#    NOT committed -- it is kept offline for the one scenario where the key must be revoked
#    without still holding the private key.
```

After step 6, update this file's §1 fingerprint field and open a small follow-up PR publishing
`docs/release/flake-release-signing-public.asc` and the real fingerprint — no other repository
change is needed to go from `PENDING_ONE_TIME_KEY_CREATION` to `READY`.

## 3. CI secret injection (already implemented)

`scripts/release/sign_linux.sh` supports two production input shapes:

- `GPG_KEY_ID=<id>` — a key already present in the running environment's own keyring
  (unchanged original behavior).
- `GPG_PRIVATE_KEY=<armored key>` (optionally with `GPG_KEY_PASSPHRASE` and
  `GPG_KEY_FINGERPRINT`) — the key is imported into a **fresh, ephemeral `GNUPGHOME`** created
  for that single script invocation, never the runner's persistent keyring, and that directory
  is deleted (`trap cleanup EXIT`) whether the run succeeds or fails. If `GPG_KEY_FINGERPRINT`
  is set, the script refuses to sign unless the imported key's own fingerprint matches exactly
  — protecting against a corrupted or substituted secret silently signing under the wrong
  identity. The private key material and passphrase are never echoed, written to a script
  argument visible in `ps`, or left on disk outside that ephemeral, deleted directory.

A production release job supplies these as encrypted GitHub Actions secrets:

```yaml
- name: Sign checksum manifest and .deb package
  env:
    GPG_PRIVATE_KEY: ${{ secrets.GPG_PRIVATE_KEY }}
    GPG_KEY_PASSPHRASE: ${{ secrets.GPG_KEY_PASSPHRASE }}
    GPG_KEY_FINGERPRINT: ${{ secrets.GPG_KEY_FINGERPRINT }}
  run: |
    scripts/release/sign_linux.sh dist/flake-*.sha256
    scripts/release/sign_linux.sh desktop/src-tauri/target/release/bundle/deb/*.deb
```

This exact mechanics — ephemeral import, fingerprint pinning, redaction, cleanup — is proven
live in CI today, fed a disposable throwaway key instead of the real secret, by the
`linux-release-signing-test` job in `.github/workflows/t05-04-signing-pipeline-test.yml`
(`TEST_SIGNING_MODE=1` together with `GPG_PRIVATE_KEY` set to an in-job-generated disposable
key — still labeled `TEST_SIGNING_IDENTITY_ONLY=YES`/`PRODUCTION_SIGNATURE_CLAIMED=NO`
throughout, never claiming production). The only thing that changes once the real secret exists
is which key material is injected — no script change is required.

## 4. Verification (for anyone downloading a release)

```bash
# Import the published public key once:
gpg --import docs/release/flake-release-signing-public.asc

# Confirm the fingerprint matches the one published in this document and in the release notes
# BEFORE trusting any signature made with it:
gpg --list-keys --with-colons "285091250+TheHalfMoon@users.noreply.github.com" \
  | awk -F: '/^fpr:/ {print $10; exit}'

# Verify a downloaded artifact against its detached signature:
gpg --verify flake-<version>-linux-x86_64.tar.gz.asc flake-<version>-linux-x86_64.tar.gz
gpg --verify flake_<version>_amd64.deb.asc flake_<version>_amd64.deb
```

A verification failure (bad signature, unknown key, or a fingerprint mismatch against the one
published here) means the artifact must not be trusted or installed — fail closed, never warn
and continue.

## 5. Rotation and revocation

- **Planned rotation** (e.g. approaching `Expire-Date`, or a routine security refresh):
  generate a new key following §2 with a new Founder decision recording the change (this
  document's §1 identity string does not change — only the key material and fingerprint do,
  unless the Founder also decides to change the identity itself); publish the new public key
  and fingerprint alongside the old one for one full release cycle so in-flight verifications
  do not break; update the three GitHub Actions secrets; keep the old public key published,
  marked superseded, so historical release signatures remain verifiable.
- **Compromise or suspected compromise:** stop using the CI secrets immediately (rotate/delete
  them in GitHub Settings), publish the offline revocation certificate from §2 step 3 (`gpg
  --import flake-release-signing-revocation.asc` then re-publish the now-revoked public key),
  and generate a fresh key under a new Founder decision before any further Linux release is
  signed. Never reuse a key once its revocation certificate has been published.
