# Founder Direction Addendum — Linear-Class Product Execution

**Status:** FOUNDER DIRECTION ADDENDUM / NON-AUTHORIZING  
**Date:** 2026-08-31  
**Applies to:** Fehrest V2 proposal set  
**Execution effect:** NONE while R1 remains open  
**Canonical frontier:** `specs/CURRENT.md`

> This addendum records a clarification of the V2 founder direction. It does not reinterpret R1, activate Spec 002, authorize implementation, modify sealed benchmark semantics, or supersede canonical governance.

---

## 1. Founder clarification

Linear is **added to** the Fehrest long-term product plan. Linear does **not replace** the existing Fehrest product direction.

The existing scope remains intact:

```text
Memory Repository
+ Obsidian-class personal knowledge
+ Notion-class structured workspace
+ Slack/Zulip-class communication
+ GitHub-class integration/review discipline
+ arbitrary human + agent memory
+ local-first ownership
+ provenance and temporal truth
+ Search / Ask / Graph
+ collaboration and sync
+ enterprise administration
+ mobile
+ extensions and automation
+ Fehrest Hub/network effects
```

The additive requirement is:

```text
+ LINEAR-CLASS PRODUCT PLANNING, EXECUTION, TRIAGE,
  CUSTOMER INTELLIGENCE, ANALYTICS, CODE REVIEW,
  AGENTIC DELIVERY AND AUTOMATION
```

Therefore:

```text
LINEAR_ADDED_TO_PLAN=YES
LINEAR_REPLACES_EXISTING_V2_SCOPE=NO
EXISTING_PRODUCT_PILLARS_RETAINED=YES
MEMORY_REPOSITORY_REMAINS_CORE_PRIMITIVE=YES
```

## 2. Expanded category thesis

Fehrest should become one coherent local-first workspace in which people and agents can:

```text
remember
write
research
communicate
plan
prioritize
triage
execute
review
ship
learn
and preserve why the work happened
```

Linear is a mandatory benchmark for the `plan -> execute -> review -> ship` portion of that product.

Obsidian remains a mandatory benchmark for personal/local knowledge.
Notion remains a mandatory benchmark for docs and structured workspace.
Slack and Zulip remain mandatory benchmarks for communication.
GitHub remains a flagship integration and benchmark for code/review/workflow discipline.
Agent-memory systems remain mandatory benchmarks for durable machine context.

No benchmark replaces the others.

## 4. Living competitor rule

Linear is actively evolving. Fehrest must not freeze its parity target to a one-time screenshot of Linear.

A future maintained capability registry must track:

```text
LINEAR_CAPABILITY_ID
LINEAR_SOURCE
OBSERVED_DATE
CAPABILITY_STATUS
FEHREST_OWNER_SPEC
FEHREST_PARITY_STATUS
PARITY_TEST
SURPASS_REQUIREMENT
MIGRATION_REQUIREMENT
MOBILE_REQUIREMENT
API_REQUIREMENT
AGENT_REQUIREMENT
SECURITY_REQUIREMENT
DEFER_OR_REJECT_RATIONALE
```

When Linear adds a materially new product-development capability, the registry is reviewed and the capability receives one of:

```text
PARITY_REQUIRED
OUTCOME_REQUIRED_DIFFERENT_IMPLEMENTATION
INTEGRATE_INSTEAD_OF_BUILD
DEFER_WITH_REASON
REJECT_WITH_REASON
```

A capability may not disappear merely because Fehrest uses different terminology.

---

## 5. Parity is not imitation

Fehrest does not need to copy Linear's internal architecture, terminology, pricing model, or exact UI.

The product rule is:

> Match or exceed the important user outcome; preserve Fehrest's own canonical memory, local-first, provenance, temporal, security and agent-authority model.

Examples:

```text
Linear issue         -> Fehrest Work Item / Task outcome
Linear initiative    -> Fehrest strategic work hierarchy outcome
Linear cycle         -> Fehrest bounded planning iteration outcome
Linear Triage        -> Fehrest work intake + routing outcome
Customer Requests    -> Fehrest customer evidence -> work trace outcome
Linear Diffs         -> Fehrest native review outcome backed by forge integration
Coding session       -> Fehrest delegated execution session through replaceable providers
Loops                -> Fehrest scheduled/event-driven agent automation outcome
```

Exact names remain a later product-design decision.

A future Linear replacement claim is not permitted merely because Fehrest has tasks and projects.

A mature readiness review should require evidence equivalent to:

```text

CRITICAL_LINEAR_PARITY_GAPS=0
UNTESTED_CRITICAL_LINEAR_WORKFLOWS=0
```

---

## 9. Sequencing rule

This direction does not authorize building every Linear-class capability immediately.

The governing rule remains:

```text
CATEGORY VISION = BROAD
ACTIVE SPEC = NARROW
ONE ACTIVE FRONTIER
```

Linear-class capabilities are mapped into the V2 program through an additive track and explicit owning specs/gates. They do not bypass R1, provenance reconciliation, Constitution/architecture reconciliation, Spec 002, or any later entry gate.
