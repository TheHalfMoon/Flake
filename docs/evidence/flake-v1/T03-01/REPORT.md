## Architecture: a new `SourceCheck` kind, not a `Source` mutation — and why three already-merged modules needed a small, structural extension

**`SourceCheck` is `Relation`'s exact architectural shape, applied to a new problem.** Exactly like `T02-03`'s `Relation`, `SourceCheck` is an ordinary opaque-payload canonical object committed through the existing `CommandTarget::CreateObject` — no new `CommandTarget` variant, no schema change, no event store. §15's own "Source check" row is explicit that this is "an append-only observation, not a rewritten revision" — `source_check::check_source` therefore never mutates the `Source` it inspects, even when it observes `Changed`; it only ever creates one new, permanent `SourceCheck` object per invocation.

**The locator gap this task closes.** `capture::import_file` left `Source::claimed_path` at `None` unconditionally for every file import before this task (confirmed directly in the merged `T02-02` code, not assumed) — there was nothing yet that needed to reopen the original path. §15 already names "owner-selected locator hint" as part of `Source`'s own row; this task populates the field that was already declared but never filled in. It remains exactly as non-authoritative as the pre-existing `claimed_repository`/`claimed_commit` fields: a hint of where to look on *this* machine, never filesystem/read authority on its own, and never re-followed automatically — every path this module opens is opened only in direct, synchronous response to one explicit caller invocation (`source-check`/`source-reselect`/`source-admit-change`), never a background watcher.

**Why three already-merged modules needed a change (necessary, not "unrelated refactoring").** Introducing a *seventh* canonical record kind is structurally different from extending an existing kind's lifecycle: three functions in this crate exhaustively match on every `RecordPayload` variant (`export::project_scope_object_ids`'s per-kind listing union, `import.rs`'s `validate_self_contained`/`rewrite_references`, `index.rs`'s `searchable_text`, `project::list_project_records`'s exclusion arm) and the compiler enforces exhaustiveness on the enum itself. Every one of `T02-01`→`T02-06`'s own new-kind tasks needed the identical class of touch when they landed (`Source`, then `Relation`) — this is the established, unavoidable cost of "no new `CommandTarget`, no schema change, just another `RecordPayload` variant," not scope creep. Each touch is a minimal, mechanical addition (one new match arm, or one new line in an existing union), documented at its exact call site.

**`export.rs`'s union is the one that matters for correctness, not just compilation.** `project_scope_object_ids` (T02-05) explicitly unions each kind's own listing function; without adding `source_check::list_project_source_checks` to that union, a project-scoped export would silently drop every `SourceCheck` belonging to that project — precisely the class of omission `T02-07`'s own independent verifier exists to catch, and precisely the failure mode §16 forbids ("full declared state is readable," I06/I10). `project_export_includes_source_checks` (new test, `export.rs`) proves this directly: it imports a file, runs one check, and asserts the resulting project-scoped export actually contains a `"kind": "source_check"` revision file — not merely that the crate compiles.

**`import.rs`'s new pass reuses `Relation`'s own established re-pinning pattern for the one field that cannot be preserved.** `import_selected_merge`'s existing `Relation` pass already establishes the pattern this task needed: an endpoint's pinned `revision_id` cannot survive replay (the destination always mints a fresh one — verified directly against `canonical.rs`'s commit code by `T02-06`, not assumed), so the caller re-pins it to the destination's actual current revision *after* the referenced object has its own destination identity. `SourceCheck.checked_revision_id` is exactly this same class of field (a revision reference, not an object reference), so the new pass added between the initial four-kind pass and the `Action` subpasses does the identical thing: remap `source_id` through `id_map` (already resolved, since `Source` is imported in the pass immediately before), then set `checked_revision_id` to the destination `Source`'s actual current revision at import time. `merge_source_check_source_id_is_rewritten_and_checked_revision_repinned` (new test, `import.rs`) proves both halves directly.

**Why `source_check::observe` deliberately does not reuse `capture::capture_file` (a documented non-reuse, not an oversight).** `capture_file` already exists, is already-audited, and its exact error-message text ("missing or unreachable", "symlink not followed (S03)", "not a regular file", "exceeds limit") is already asserted verbatim by `T02-02`'s own merged tests. This module's classification need is materially different: a recheck must distinguish **Missing** from **Denied**, an outcome taxonomy `capture_file` was never designed to report (it only ever needs one outcome: refuse the whole import). `relation.rs` already documents this identical tradeoff for its own non-reuse of `temporal::validate_supersession` ("reuse the algorithm shape, not the code, when the surrounding contract differs") — `source_check::observe` is that same choice applied here: the same symlink-then-regular-file-then-bounded-read shape, reimplemented standalone with its own outcome taxonomy. `capture::capture_file` itself *is* reused, unmodified, by `admit_changed_source`, where the contract (build one brand-new, fully-defended `Capture`) is identical to import's own — this is the T02-06-style "direct counterpart, reuse" choice, made explicitly alongside the non-reuse choice above, in the same module doc comment.

**Owner admission is structurally separated from observation.** Three distinct, separately-invocable functions exist, deliberately: `check_source` (pure observation, never mutates `Source`), `reselect_source` (explicit relocation, refuses unless the new location's bytes are digest-identical to the last saved capture — "Reselection after move verifies digest and preserves source identity/history"), and `admit_changed_source` (explicit admission of changed bytes, optionally combined with a new path, always re-opening and re-hashing fresh rather than trusting a possibly-stale prior `SourceCheck` digest — no gap between "what was checked" and "what was admitted"). Both mutating functions require the caller's own `expected_revision_id`, enforced by the same `CanonicalWriter::commit` expected-revision-conflict check `T01-03`/`T01-07` already proved (F21/I05) — a stale decision cannot silently clobber a newer observation.

## Security boundary — what this task actually enforces (S03/S07)

- **A symlink swapped in after admission is refused, never followed.** `recheck_refuses_a_symlink_swapped_in_after_admission` (new test) imports a file, then replaces it with a symlink pointing at different content and reruns `check_source` — the recheck reports `Denied`, with no digest ever computed from the symlink target. This is the concrete adversarial case named by this task's own security clause: "one selected source path does not authorize its repository, parent directory or credentials." **Honest environment limitation:** on this development host, Windows file-symlink creation without Developer Mode/elevation fails with `ERROR_PRIVILEGE_NOT_HELD` (os error 1314) — confirmed directly by a standalone probe (`raw/13-symlink-privilege-probe.txt`), the identical limitation `capture.rs`'s own pre-existing `refuses_a_symlink_without_ever_opening_the_target` test already documents and conditionally skips on. This test carries the identical `#[cfg(windows)]` skip-if-unavailable guard; it did **not** exercise the symlink path on this run (confirmed by rerunning the probe immediately before this evidence was captured). The `Denied` code path it would exercise is, however, independently and unconditionally proven by the next test below, which reaches the same `RawObservation::Denied` branch through a different, always-reproducible trigger.
- **A path that stops being a regular file is refused, unconditionally reproducible.** `recheck_reports_denied_when_the_path_becomes_a_directory` deletes the previously-captured file and creates a directory at the exact same path, then reruns `check_source` — `Denied`, no digest computed. This exercises the same `!meta.file_type().is_file()` branch a symlink-swap would also hit, and is not environment-dependent.
- **No path other than the source's own already-recorded locator, or one explicit caller-supplied path, is ever opened.** No directory walk, no glob, exists anywhere in `source_check.rs` — structurally, not by a runtime check, matching `capture.rs`'s own already-established discipline.
- **No Git subprocess, remote fetch, or watcher exists anywhere in this module** — grepped and confirmed absent. `claimed_commit`/`claimed_repository` are completely untouched by this task and are never read by anything in `source_check.rs` (F14: "no fetch attempted; reference cannot be locally verified" — those fields remain purely descriptive, exactly as `T02-02` already documented).
- **Owner admission cannot be bypassed by a stale caller.** `admit_changed_source_requires_the_correct_expected_revision` proves a stale `--expect` is refused with an "expected revision conflict"-class error before any mutation.
- **A move with different content is refused, not silently admitted.** `reselect_source_refuses_a_move_with_different_bytes` proves `reselect_source` leaves the `Source` completely untouched and points the caller at `source-admit-change` instead — moving and content-changing are never conflated into one implicit action.

## `Unchecked` is derived, not stored — a deliberate reading of §15's wording

§15's "Source check" row lists the possible recorded values as "observed digest or Missing/Denied/Unchecked." This task stores exactly four `CheckStatus` variants (`Match`/`Changed`/`Missing`/`Denied`) as actual `SourceCheck` objects — there is no persisted `Unchecked` variant. Rationale, stated here explicitly rather than left implicit: "Unchecked" describes the *absence* of any observation for a source, which is already a fact a reader can determine without a manufactured record, by finding zero rows in `source_check::list_checks_for_source`. Manufacturing an explicit `Unchecked` canonical object at admission time (or on every read) would be exactly the kind of "derived fact minted as canonical state" I06 forbids — a canonical object should represent something that was actually observed, not the absence of an observation. `list_checks_for_source`/`list_project_source_checks` are the read path a CLI or UI layer would use to render "Unchecked" as a derived label when history is empty; `check_history_is_append_only_and_chronological` proves the append-only, chronological history these reads depend on.
